This source-first audit maps every visible leaf row in the W3C Music Notation
Reference to the current Viritura MNX ingest/model/engraving pipeline and the
MusicXML/MXL importer. It does not claim editor-authoring, playback, export,
or round-trip support unless a row note says so.

## Status legend and method

| Code | Meaning                                                                       |
| ---- | ----------------------------------------------------------------------------- |
| S    | Supported for the column's scope.                                             |
| P    | Partial, approximate, or fixed-style support.                                 |
| N    | Unsupported; no matching implementation path was found in the audited source. |
| NA   | Not applicable to the importer's scope; behavior is derived after import.     |
| ?    | Invalid or unrecognized upstream status value.                                |

- **MNX** and **MusicXML** reproduce the upstream notationref format levels.
  Their descriptor text remains upstream and is not duplicated here.
- **Viritura MNX** requires that Viritura can ingest/model and
  meaningfully engrave the concept. Schema acceptance by itself is not enough.
  A fully implemented documented `_x.viritura` path counts as supported; the
  upstream MNX column separately exposes that it is not standard MNX.
- **Viritura MusicXML/MXL importer** means Viritura's current converter. It
  requires an implemented mapping for the MusicXML construct; `.mxl` is only
  the ZIP container and has the same notation coverage as XML input.
- This audit does **not** use the separate **MNXconverter** support matrix loaded
  by notationref. That converter is a different implementation unrelated to
  Viritura and must not be read as Viritura importer coverage.
- Existing Viritura coverage docs were treated as leads, not proof.
- Row notes are retained only for `P` and `?` Viritura statuses. They explain
  the remaining feature boundary without pinning the audit to source paths.
- A conservative `N` is used where only a generic text escape hatch exists
  without the row's semantic or graphical behavior.
- Upstream inputs:
  [`music-notationref/concepts.json`](https://github.com/w3c-cg/music-notationref/blob/main/concepts.json),
  [`mnx/docs/notationref.json`](https://github.com/w3c-cg/mnx/blob/main/docs/notationref.json),
  and
  [`musicxml/notationref.json`](https://github.com/w3c-cg/musicxml/blob/gh-pages/notationref.json).

### Highest-confidence findings

- Upstream data currently contains a `rest-1024th` format entry that is absent
  from the visible taxonomy, and MNX assigns the invalid level `0` to
  `struct-staff-hide-specific`. The updater reports these anomalies without
  treating them as Viritura coverage.
- Viritura's strongest MNX-pipeline coverage is conventional pitched notation,
  rhythms/rests, common signatures/barlines, voices, repeats, and explicit
  system/page layout. Advanced tablature remains entirely unsupported.
- Viritura's MusicXML/MXL importer supports core notation outright and additional
  concepts partially. Many partial rows require `includeVendorExtensions`,
  which is off by default.
- The importer rounds MusicXML decimal pitch alterations to integers, so
  microtonal pitches are corrupted rather than merely losing their display glyph.
- MusicXML 22ma/22mb octave shifts fall through to 8va/8vb, and unrecognized
  dynamic spellings fall back semantically to `f`.
- Standalone tempo directives such as `rit.`, `accel.`, and `a tempo` are
  discarded unless the same measure also yields a numeric tempo object.
- A first-part key signature is skipped whenever its initial attributes also
  contain transposition; this avoids treating a written key as concert pitch but
  currently loses the key instead of converting it.
